10:00–10:25 | Mini 4 — El Escudo

Di “El modelo dice qué datos guarda la tabla. El serializer revisa los datos que llegan por la API y también prepara los datos que salen. Hoy vamos a ponerle una regla: el valor de un contrato no puede ser negativo.”

Señala: abre Backend/contratos/serializers.py. El reto pide crear un ModelSerializer para Contrato y poner la regla de valor mínimo en su clase Meta.

from rest_framework import serializers
from .models import Contrato


class ContratoSerializer(serializers.ModelSerializer):
    class Meta:
        model = Contrato
        fields = '__all__'
        extra_kwargs = {'valor_total': {'min_value': 0}}
  • ModelSerializer crea los campos del serializer usando el modelo.
  • model = Contrato conecta el serializer con ese modelo.
  • fields = '__all__' incluye los campos del modelo en la API.
  • extra_kwargs agrega una regla adicional: valor_total debe ser como mínimo cero.
Di “Cuando llega un contrato, el serializer revisa la regla antes de guardarlo. Si el valor es negativo, responde que los datos no son válidos y no crea el registro.”

Haz: deja que escriban el serializer y pregunta qué pasaría si el cliente envía valor_total = -1. Esperamos que Django lo rechace con HTTP 400.

Precisión para explicar: el primer ataque es JSON válido, pero incompleto y con un valor incorrecto; comprueba la validación de campos. El segundo es un contrato completo con valor negativo; comprueba específicamente min_value. Es más claro decir “datos inválidos” que “JSON malformado”.

El panel necesita que exista /api/contratos/. Si ahora da 404, termina el Mini 5 y vuelve a probar el Mini 4 después de configurar CORS.

10:35–10:50 | Crear la vista

Di “Un endpoint es una dirección de la API. Para la colección de contratos usaremos un ViewSet de Django REST Framework. El ViewSet conecta las operaciones HTTP con nuestro modelo y serializer.”

En Backend/contratos/views.py

Agrega los imports y la vista. Conserva el resto del archivo.

from rest_framework import viewsets
from .models import Contrato
from .serializers import ContratoSerializer


class ContratoViewSet(viewsets.ModelViewSet):
    queryset = Contrato.objects.all()
    serializer_class = ContratoSerializer
Explica: ModelViewSet trae las operaciones habituales de la API. queryset indica qué contratos consultar y serializer_class cómo validarlos y convertirlos a JSON.
Di, línea por línea “La primera línea importa el tipo de vista. Las dos siguientes traen el modelo y el serializer. Creamos ContratoViewSet; le decimos qué contratos manejar y qué serializer usar.”

Haz: dales unos minutos para escribirlo y guardar. Pide a una pareja que señale en el código qué línea elige los datos y cuál elige el serializer.

Pregunta al grupo “Si cambiáramos el modelo, ¿qué parte de esta vista nos dice qué registros ofrecer?” Respuesta: queryset.

10:50–10:58 | Registrar las rutas

En Backend/contratos/urls.py

Importa el ViewSet, regístralo y añade las rutas del router. No borres la ruta estado/.

from .views import EstadoJardinView, ContratoViewSet

router.register('contratos', ContratoViewSet, basename='contrato')

urlpatterns = [
    path('estado/', EstadoJardinView.as_view(), name='estado-taller'),
    *router.urls,
]
Di “El router crea las rutas a partir del ViewSet. La configuración principal ya agrega el prefijo api/; junto con contratos/, forma /api/contratos/.”
Di, mirando el código “Importamos el ViewSet para que este archivo lo conozca. router.register conecta ese ViewSet con la ruta contratos/. basename es el nombre interno de esas rutas. Conservamos estado/, que usa el panel, y router.urls agrega las rutas nuevas.”

Haz: pide que sigan la ruta en los dos archivos: config/urls.py agrega api/; contratos/urls.py agrega contratos/. Juntas forman la dirección completa.

11:05–12:00 | Conectar CORS y cerrar

11:05–11:20 | Entender qué está bloqueando el navegador

Di “La ruta responde cuando la abrimos directamente, pero React intenta leerla desde otra dirección. React usa el puerto 5173 y Django el 8000. El navegador aplica CORS para decidir si deja que React lea esa respuesta.”
Aclara: que ambos servidores estén en el mismo computador no los convierte en el mismo origen. El protocolo, el nombre del host y el puerto forman el origen. localhost:5173 y localhost:8000 son distintos.

Demuestra: abre F12 → Console y vuelve a ejecutar la prueba de React. Señala que el mensaje CORS aparece en el navegador. Luego abre la API directamente en otra pestaña: esto permite separar “la ruta responde” de “React puede leerla”.

Pregunta al grupo “¿CORS es una conexión a PostgreSQL?” Respuesta: no. Es un permiso para que el navegador lea una respuesta entre orígenes distintos.

11:20–11:35 | Configurar el permiso

Di “Django necesita declarar qué orígenes acepta. Permitiremos solo las dos direcciones locales que usamos para abrir Vite.”

En Backend/config/settings.py, agrega corsheaders a INSTALLED_APPS:

'corsheaders',

En MIDDLEWARE, ubica su middleware antes de CommonMiddleware:

'corsheaders.middleware.CorsMiddleware',
'django.middleware.common.CommonMiddleware',

Agrega la lista de orígenes permitidos:

CORS_ALLOWED_ORIGINS = [
    'http://localhost:5173',
    'http://127.0.0.1:5173',
]
Explica: el origen incluye protocolo, dirección y puerto. Se permiten los dos nombres locales porque Vite puede abrirse con cualquiera. No uses * para permitir todos los sitios.
El paquete django-cors-headers ya está en requirements.txt. Si no está instalado en el entorno virtual, ejecuta python -m pip install -r requirements.txt desde Backend/.

Haz: que los estudiantes ubiquen cada cambio y expliquen su propósito antes de guardar. Comprueba que el middleware está antes de CommonMiddleware y que los orígenes tienen protocolo y puerto, sin agregar una barra final.
