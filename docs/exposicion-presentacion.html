Hola, somos Steven y Yesid. Durante tres días construiremos una plataforma para explorar contratos públicos colombianos de SECOP II. Antes de programar, quiero que entendamos cómo se conectan la pantalla, la API y la base de datos.

Diapositiva 3 · Primero, una pregunta

2 min
Piensen unos segundos y elijan A, B o C. No hay que adivinar una palabra técnica; piensen dónde debe vivir un contrato si varias personas necesitan consultarlo.

Matiz: el navegador sí guarda el progreso de las misiones en su almacenamiento local. Eso no significa que los contratos estén ahí. Los contratos se guardan en PostgreSQL.

Diapositiva 4 · Full Stack: tres capas

2 min
Una aplicación Full Stack conecta tres capas. El frontend es lo que usa la persona. El backend recibe sus solicitudes y aplica las reglas. La base de datos conserva la información para que no se pierda al cerrar la página.
Relaciona cada capa con el proyecto: React y Vite para el frontend; Django y Django REST Framework para el backend; PostgreSQL para la base de datos.
¿Por qué no dejamos que React se conecte directamente a PostgreSQL? Porque expondríamos credenciales y perderíamos el control central de las reglas.
Hace falta una forma acordada para que React le pida información a Django. Esa forma es la API.

Diapositiva 5 · API REST: el mesero

3 min
Pensemos en un restaurante. React es el comensal: pide un dato. La API lleva el pedido a Django. Django consulta PostgreSQL y prepara la respuesta. El cliente no entra directamente a la base, igual que el comensal no entra a la cocina.
Señala las cuatro partes del dibujo y lee el ejemplo real: /api/contratos/ es la dirección de la colección de contratos.
Si pido un contrato que no existe, ¿debería devolverme uno inventado o avisar que no lo encontró? La API debe responder con un estado claro, como HTTP 404.
Veamos qué ocurre desde el clic del usuario hasta la respuesta en JSON.

La API: viaje de datos, métodos y formato

Diapositiva 6 · El viaje de una solicitud

3 min
Sigamos una petición GET a /api/contratos/. React la envía con fetch. Django revisa la ruta y llama a la vista. El ViewSet usa el modelo y el ORM para consultar PostgreSQL. El serializer prepara el JSON. React recibe la respuesta y la muestra.
Recorre los seis pasos de izquierda a derecha y luego de arriba abajo. Si algo falla, revisamos Network en F12 y la terminal de Django para localizar en qué parte se detuvo.
Si Django encuentra el contrato pero React no lo muestra, ¿qué pasos revisarían antes de tocar la base de datos?
La URL identifica el recurso; el método HTTP indica qué queremos hacer con él.

Diapositiva 7 · Los verbos HTTP son CRUD

2 min
GET lee datos. POST envía datos para crear. PUT o PATCH actualizan. DELETE elimina. En Django REST Framework, ModelViewSet ya trae estas acciones para el modelo Contrato.
Relaciona la tabla con los minis. GET se usa para consultar contratos e informes. POST aparece en la validación del Mini 4 y en la descarga masiva del Mini 11. DELETE se protege con confirmación en el Mini 15.
PUT y PATCH están disponibles en el ViewSet, pero no son el tema de una misión independiente en este taller. El Mini 13 trata búsqueda, filtro por estado y ordenamiento.
Para que dos lenguajes distintos intercambien estos datos, usamos un formato común: JSON.

Diapositiva 8 · JSON, el idioma común

2 min
Django está escrito en Python y React en JavaScript. JSON es texto estructurado que ambos pueden leer. Las llaves rodean un contrato; los corchetes pueden rodear una lista de contratos. Cada clave tiene un valor.
Señala id_contrato, entidad_compradora, valor_total y estado. En este ejemplo, el valor decimal viaja como texto para conservar sus dos decimales. Es una muestra de los campos reales del proyecto.
¿Cuál de estos datos identifica de manera única el contrato? ¿Qué campo describe su estado?

Diapositiva 9 · Nuestro stack completo

3 min
React y Vite muestran la interfaz en el puerto 5173. Django REST Framework atiende la API en el 8000. PostgreSQL es un servicio aparte en el 5432. React y Django se hablan con HTTP y JSON; Django consulta la base.
Señala las flechas y los tres puertos. Aclara que son dos servidores web y un servicio de base de datos, y que por eso tenemos varias terminales.
CORS: para el navegador, el puerto forma parte del origen. 5173 y 8000 son orígenes distintos. Django debe autorizar el origen del frontend para que React pueda leer la respuesta.

Diapositiva 11 · Modelo, ORM y migraciones

15 min
Un modelo es una clase Python que describe una tabla. Cada campo es una columna. El ORM traduce operaciones de Python a consultas SQL. Una migración guarda y aplica cambios en la estructura de PostgreSQL.
Pregunta qué datos necesita un contrato y luego señala los campos: ID, entidad, descripción, valor, estado y fecha de firma. Explica que el identificador es único.
El código visible usa la forma corta de algunos argumentos para que el ejemplo quepa. En el proyecto escribimos sus nombres completos, como max_length=60 y decimal_places=2. Agregamos también Meta.ordering y __str__ al completar el modelo.
Explica el flujo inferior: el modelo cambia, makemigrations genera el archivo de migración y migrate lo aplica. No digas que makemigrations crea la tabla.
python manage.py makemigrations contratos

Detecta el nuevo modelo y genera el archivo de migración.

python manage.py migrate

Ejecuta la migración en PostgreSQL y crea contratos_contrato.

¿Qué error aparecería si intentamos consultar Contrato antes de aplicar la migración?
Cuando la tabla existe, podemos administrarla desde el panel que Django ya trae.

Diapositiva 13 · Serializer: el traductor

12 min
El objeto Contrato está en Python, pero React recibe JSON. El serializer traduce la respuesta y valida los datos que llegan para crear un contrato. ModelSerializer genera los campos usando el modelo.
Señala model y fields. Después explica extra_kwargs: cambia la regla del campo valor_total sin volver a declarar el serializer completo. min_value cero impide contratos con valor negativo.
Si el navegador envía valor_total como texto que no es un número o envía un valor negativo, ¿qué respuesta esperamos? HTTP 400 con el error de validación.
Si el panel no puede llamar al endpoint por CORS, la configuración se completa en el Mini 9. Después se repite la prueba del serializer.
Ya tenemos el modelo y su traductor. Ahora conectamos una dirección con las acciones de la API.

Diapositiva 14 · Vistas y rutas

15 min
ContratoViewSet hereda de ModelViewSet y obtiene las acciones CRUD. queryset define con qué contratos trabaja. serializer_class define cómo los convierte y valida. DefaultRouter genera las direcciones para la colección y los registros individuales.
Sigue el prefijo en tres partes: config/urls.py incluye contratos.urls bajo api/. El router registra contratos. Juntas forman /api/contratos/.
GET /api/contratos/

Consulta la colección y debe responder HTTP 200.

GET /api/contratos/999999/

Consulta un registro que no existe y debe responder HTTP 404.

La ruta directa se puede probar en el navegador. El panel React puede necesitar que completemos CORS en el Mini 9 antes de leer la respuesta.
Con el backend en su lugar, pasamos a los componentes que muestran los datos en React.

React y la conexión con Django

Diapositiva 16 · Estado: la memoria de React

3 min
Una variable normal puede cambiar sin que React se entere; por eso la pantalla no necesariamente se actualiza. useState guarda el dato y devuelve una función que lo cambia. Cuando usamos esa función, React vuelve a dibujar el componente.
Explica el contador del Mini 7: cuenta inicia en cero, setCuenta suma uno. data-cuenta y data-aumentar son atributos que el verificador usa para localizar el número y el botón.
¿Qué debería aparecer después de pulsar una vez? El valor inicial más uno.
Ya sabemos guardar y actualizar estado. Ahora hacemos una petición a Django.

Diapositiva 17 · CORS: el portero del navegador

5 min
React está en el puerto 5173 y Django en el 8000. Para el navegador eso significa orígenes distintos. CORS es la regla de seguridad que le permite a Django decir qué origen puede leer sus respuestas.
Recorre las tres piezas de settings.py: corsheaders en INSTALLED_APPS, CorsMiddleware antes de CommonMiddleware y los dos orígenes locales exactos. La librería ya está en requirements.txt; el reto es configurarla.
¿Quién bloquea la lectura de la respuesta, Django o el navegador? El navegador, si la respuesta no incluye el permiso esperado.
Después de cambiar settings.py, reinicia runserver. En F12, pestaña Network, observa OPTIONS y luego GET.
Con CORS configurado, React puede leer el resultado del fetch y renderizar la lista.

Diapositiva 25 · Todo conectado

3 min
El modelo define qué datos hay. El serializer valida esos datos y los convierte a JSON. La vista decide qué hacer. La ruta indica dónde atender la petición. React usa fetch, guarda la respuesta en su estado y muestra los contratos.
Recorre las flechas de backend y frontend. Enfatiza que el JSON es el puente entre Django y React.
