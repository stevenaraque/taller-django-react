Por qué exactamente 8000 y 5173: son los números de fábrica de cada herramienta. Cómo se entiende un puerto: el computador tiene una sola dirección local (127.0.0.1) pero ejecuta varios programas que "atienden" a la vez. El puerto es el número de despacho: el sistema operativo le entrega a Django lo que llega al 8000 y a Vite lo que llega al 5173. Dos programas en la misma máquina, cero conflicto.

Cómo se conectan Django y React (la pregunta del día): los dos programas NO se hablan directamente. Por eso el permiso es asunto del navegador, no de Django ni de React: esa regla es CORS y por eso el día se llama "El Portero".

Detalle de 127.0.0.1: es la dirección de retorno (loopback): significa "esta misma máquina". Una petición hacia 127.0.0.1 nunca sale a internet ni a la red del colegio: gira por dentro del propio equipo. Por eso el taller funciona sin internet: base de datos, backend y frontend viven en la misma máquina y se hablan por dentro.

Dices:

Empezamos por la pieza chica. Escribimos function EtiquetaSecop. Es una función normal de JavaScript. Dónde: en el mismo archivo, debajo del componente anterior.

export default function Camaleon() { return ( <section> <EtiquetaSecop /> <h1 className="titulo-gigante">Contratos públicos de Colombia</h1> <p>Explora quién compra, cuánto paga y en qué estado va cada proceso.</p> </section> ) }
Dices:

Ahora el componente principal. export default es la puerta por donde el juez del panel trae este componente para probarlo. Sin esa palabra el archivo existe pero el mini no carga. El nombre function Camaleon es el nombre exacto que el juez busca.

El return va con paréntesis para que el JSX de varias líneas quepa completo sin romperse.

La section es el elemento raíz. Un componente devuelve una sola etiqueta que contenga todo lo demás, y aquí esa etiqueta es la section.

Eso se llama composición: construir una pieza una vez y usarla donde haga falta. Si mañana el texto de la etiqueta cambia, se cambia en un solo lugar y no en diez.

El h1 lleva className y no class, porque JSX es JavaScript y class ya significa otra cosa en ese lenguaje. El título del ejemplo es Contratos públicos de Colombia y está aquí solo de muestra: cada aprendiz escribe el suyo con sus palabras. Con el párrafo igual: la descripción de ustedes, no la copiada.

(Se explica: por qué componer y no copiar) «Escuchen la pregunta de siempre: ¿por qué no escribir el span directo? Porque si esa etiqueta hiciera falta en 10 sitios de la app, copiaría el mismo HTML 10 veces. Con el componente, cada sitio es UNA línea: y si mañana cambia el texto de la etiqueta, cambio UN solo lugar. Eso hicimos hoy: escribir una pieza una vez y usarla donde sea.»

Traducción: este párrafo es la justificación práctica de la tarea. "Componer" es armar interfaces poniendo piezas pequeñas dentro de piezas grandes. La analogía del taller directo a la sala: LEGO. Si un aprendiz insiste en que con copiar "funciona igual", concede: funciona igual HOY, y falla cuando crezca la app. Ese es todo el argumento.

Los dos conceptos de toda la sesión del Mini 6, para quedar sólidos: 1) Un componente es una función JavaScript que devuelve lo que se ve (JSX). 2) La composición (un componente usado dentro de otro) es lo que hace React distinto de escribir HTML: piezas que se reutilizan.

El navegador no entiende JSX: escribir etiquetas dentro de una función de JavaScript no es JavaScript puro: es una extensión. Antes de que el navegador ejecute el archivo, Vite lo traduce: cada etiqueta se convierte en llamadas a funciones de React. <EtiquetaSecop /> significa "ejecuta la función EtiquetaSecop y su resultado queda anidado aquí". Por eso la mayúscula es gramática, no gusto: en minúscula, React lo interpretaría como una etiqueta HTML con ese nombre (que no existe en ningún estándar) y la pantalla quedaría en blanco o explotaría con error.

Para qué sirve export default: cada archivo es un módulo: una habitación con la puerta cerrada. Lo que declares dentro no existe fuera del archivo. export default define qué atraviesa la puerta. El juez del panel hace import Camaleon from '...': si Camaleon no está exportado, no llega nada y el mini no arranca.

Describir vs mandar a mano: sin React, para cambiar la pantalla hay que agarrar el DOM a mano (crear nodos, insertarlos, quitarlos). Con React, tú describes CÓMO debe verse la pantalla según los datos, y React hace el trabajo: mantiene una copia virtual del dibujo, la compara con la anterior y toca en el DOM real SOLAMENTE lo que cambió. Con la tarjeta estática de hoy no se nota; con el contador del Mini 7 sí, porque cada clic repinta y esa comparación es lo que mantiene React rápido.

Turno 4 · 7:45 a 8:45 — Yesid: Mini 7, El Albañil (estado)

Se explica: qué es el estado y por qué React necesita useState para cambiar la pantalla.

(Se explica: por qué existe el estado) «El Mini 6 dibujó una tarjeta fija: se ve y se acabó. Ahora queremos movimiento: un contador con botón. Y aquí viene la pregunta clave: si yo hago numero = numero + 1 con JavaScript normal, ¿se mueve la pantalla? NO. El valor cambia en memoria, pero React no se entera. React solo redibuja lo que sabe que cambió. Necesitamos avisarle formalmente. Para eso existe useState: una función de React que guarda el valor y devuelve además la orden para avisar.»

Traducción: este es el concepto de estado. "Estado" = la memoria del componente mientras está en pantalla. React NO vigila variables cualquiera: solo re-dibuja lo que le avisas con la función especial set. useState(0) devuelve DOS cosas (por eso vienen los corchetes): el valor actual y la función de cambio. En el ejemplo: cuenta para leer y setCuenta para cambiar.

Paso 4. Leer el código que hizo el viaje, en voz alta

Dónde: para proyectar: Frontend, src, features, misiones, dia2, Mini8_Impulso.jsx. Ahí vive el código que el panel ejecuta.

async function impulso() { setLanzando(true) setResultado(null) try { const { respuesta } = await peticion(`${API_URL}/contratos/`) setResultado({ correcto: respuesta.ok, codigo: respuesta.status, detalle: respuesta.ok ? 'Django respondió y el navegador permitió leer la respuesta.' : 'Django respondió con un error HTTP.', }) if (respuesta.ok) alAprobar() } catch (roto) { setResultado({ correcto: false, codigo: 'sin respuesta', detalle: roto.message }) } finally { setLanzando(false) } }
Dices:

async function impulso declara una función asíncrona. Asíncrona porque el viaje a Django tarda, y JavaScript trabaja en un solo hilo: no puede quedarse congelado esperando.

Los dos primeros renglones preparan la pantalla: setLanzando pone el botón en modo impulsando, y setResultado limpia la respuesta anterior para que no se nos mezclen viajes distintos.

try abre la zona protegida. Una petición de red se puede romper, y si se rompe, el código cae directo al catch y la aplicación no se muere. Por detrás, la línea del viaje: sacamos respuesta de la petición, y await significa detente hasta que el viaje termine. La base de la dirección vive en API_URL, definida en un solo lugar del proyecto, en la carpeta shared.

setResultado guarda el desenlace y miren el detalle: el código que se muestra es respuesta.ok y respuesta.status, el resultado REAL del viaje. La aprobación nunca se inventa: se observa. Y si el viaje fue exitoso, la línea que sigue llama a alAprobar y el mini se aprueba solo.

El catch toma el error, aquí lo llamamos roto, y lo muestra como la leyenda sin respuesta junto con su motivo. Y el finally corre siempre, el viaje salga bien o mal: devuelve el botón a la normalidad. Sin el finally, si la petición fallara, el botón quedaría pegado en impulsando para siempre.

try / catch / finally: try encierra lo que puede fallar; catch corre SOLO si algo falló (recibe el error como roto) y finally corre SIEMPRE, fallara o no. El finally es el lugar de la limpieza: sin él, si la petición fallara, el botón quedaría pegado en "Impulsando..." para siempre, porque la línea que lo devuelve a la normalidad nunca correría.

Por qué esta separación importa en el trabajo real: la pantalla y el almacén de datos viven en intendencias distintas, se despliegan en servidores distintos y los corrigen equipos distintos (los que hacen la web y los que escriben el backend). Un equipo puede rehacer el diseño de React sin tocar el backend, y el backend puede agregar tablas sin tocar la pantalla: mientras el contrato de la API (las rutas y los formatos) no cambie, cada lado evoluciona solo. Eso que hoy parece una molestia (dos terminales, dos proyectos) es la arquitectura estándar del gremio.
