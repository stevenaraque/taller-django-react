7:00 a 8:00 — Mini 2: El Arquitecto

Meta: convertir la descripción de un contrato en una tabla de PostgreSQL.

Idea que debes explicar

Un modelo es una clase de Python que describe qué información guardaremos. Cada campo será una columna de la tabla. El ORM conecta esa clase con PostgreSQL para que no tengamos que escribir SQL a mano en cada consulta.

Escribir el modelo por partes

Primero, la clase y el identificador.

El nombre Contrato le dice a Django qué entidad estamos modelando. id_contrato es único porque dos contratos no deben compartir el identificador de SECOP.

Después, agregamos campos con tipos que correspondan al dato.

Texto corto para la entidad, texto largo para la descripción, decimal para dinero y fecha para la firma. estado tiene un valor por defecto para contratos creados manualmente.

Al final, definimos el comportamiento que Django usará por defecto.

Meta contiene opciones del modelo, no columnas nuevas. __str__ es un método de Python que devuelve una etiqueta clara para este contrato.

from django.db import models

class Contrato(models.Model):
    id_contrato = models.CharField(max_length=60, unique=True)
    entidad_compradora = models.CharField(max_length=180)
    descripcion = models.TextField(blank=True)
    valor_total = models.DecimalField(max_digits=16, decimal_places=2)
    estado = models.CharField(max_length=20, default='Activo')
    fecha_firma = models.DateField()

    class Meta:
        ordering = ['id_contrato']

    def __str__(self):
        return self.id_contrato

Lee el código línea por línea

LíneaQué hace y por qué la necesitamos
from django.db import modelsImporta desde Django las clases de campos que usaremos para definir las columnas.
class Contrato(models.Model)Declara la clase Contrato y la conecta con el ORM de Django. Django la interpreta como un modelo que corresponde a una tabla.
id_contrato = models.CharField(max_length=60, unique=True)Crea la columna de texto para el ID de SECOP. max_length limita el tamaño y unique=True impide guardar dos contratos con el mismo ID.

Meta: administrar contratos desde el sitio de Django sin construir otra interfaz.

Django ya trae un sitio de administración en /admin/. Es una interfaz que Django genera para ver y editar los modelos. Para que aparezca Contrato, primero importamos la herramienta de administración y nuestro modelo; después lo registramos y configuramos la lista.
Dos registros distintos: contratos en INSTALLED_APPS le dice al proyecto que cargue esta aplicación. @admin.register le dice al sitio Admin que muestre el modelo Contrato. La aplicación puede estar activa y, aun así, el modelo no aparecer en /admin/ si falta el segundo registro.

Escribir admin.py y explicar cada línea

from django.contrib import admin
from .models import Contrato

@admin.register(Contrato)
class ContratoAdmin(admin.ModelAdmin):
    list_display = (
        'id_contrato',
        'entidad_compradora',
        'estado',
        'valor_total',
        'fecha_firma',
    )
    search_fields = ('id_contrato', 'entidad_compradora', 'descripcion')
    list_filter = ('estado', 'fecha_firma')
LíneaQué hace y por qué está aquí
from django.contrib import adminImporta las herramientas del Admin de Django. Sin esto no existen admin.register ni ModelAdmin en este archivo.
from .models import ContratoTrae la clase Contrato desde models.py de esta misma aplicación. El punto significa importar desde la carpeta contratos.
@admin.register(Contrato)El decorador recibe la clase ContratoAdmin y la registra en admin.site para el modelo Contrato. Si no se ejecuta ese registro, el modelo no aparece en /admin/. La alternativa manual, escrita después de la clase, sería admin.site.register(Contrato, ContratoAdmin).
class ContratoAdmin(admin.ModelAdmin)Crea una configuración propia para el modelo y hereda las funciones del administrador estándar de Django.
list_displayElige las columnas que verá el usuario en la lista. Aquí mostramos ID, entidad, estado, valor y fecha para reconocer cada contrato.
search_fieldsAgrega el buscador del Admin para encontrar un contrato por ID, entidad o descripción.
list_filterAgrega filtros laterales por estado y fecha de firma. Sirve para reducir una lista grande sin recorrer cada fila.
Voy a leer la diferencia: importar admin trae las herramientas. Importar Contrato trae nuestros datos. El decorador registra el modelo. La clase ContratoAdmin decide cómo se verá. Sin el decorador, la configuración existe en el archivo, pero no se conecta al sitio de administración.

9:00 a 10:00 — Mini 4: El Escudo

Meta: convertir datos a JSON y rechazar datos que no cumplen las reglas.

El modelo conoce los datos dentro de Django, pero React no recibe directamente un objeto Python. El serializer lo convierte a JSON para responder y valida el JSON que llega antes de guardar. Es el traductor y también el primer control de entrada.

Escribir serializers.py

ModelSerializer enlaza la clase con el modelo.

DRF genera los campos del serializer a partir de Contrato, así evitamos repetir cada campo a mano.

Meta indica el modelo y los campos públicos.

fields = '__all__' expone todos los campos del modelo en esta API de práctica. extra_kwargs agrega una regla para valor_total.

min_value = 0 impide guardar un valor negativo.

Si el cliente envía un valor no numérico o menor que cero, DRF responde 400 con el detalle de validación.

from rest_framework import serializers
from .models import Contrato

class ContratoSerializer(serializers.ModelSerializer):
    class Meta:
        model = Contrato
        fields = '__all__'
        extra_kwargs = {'valor_total': {'min_value': 0}}

El panel hace dos pruebas: una manda un dato mal formado y otra manda un contrato completo con valor_total negativo. Las dos deben recibir HTTP 400. Ese código significa que Django entendió la petición, pero rechazó los datos.
Ojo con CORS: el navegador puede bloquear la llamada desde React hasta configurar CORS en el Mini 9. Si el código del serializer está bien pero el panel no logra llamar la API, guardamos el avance y repetimos la verificación después del Mini 9.
Verificación: ambas filas del panel deben mostrar código 400. Si aparece 404, primero hace falta la ruta del Mini 5.

10:00 a 11:00 — Mini 5: El Velocista

Meta: conectar modelo, serializer, vista y URL para exponer la API CRUD.

Ya tenemos el modelo y sabemos convertirlo a JSON. Ahora hacemos que Django reciba una petición a una dirección concreta. El ViewSet reúne las acciones CRUD y el router construye las direcciones para nosotros.

Escribir el ViewSet en views.py

ModelViewSet ya trae las acciones comunes.

Permite listar, crear, consultar un registro, actualizarlo y borrarlo. queryset define sobre qué contratos trabaja y serializer_class le indica cómo leer y validar datos.

from rest_framework import viewsets
from .models import Contrato
from .serializers import ContratoSerializer

class ContratoViewSet(viewsets.ModelViewSet):
    queryset = Contrato.objects.all()
    serializer_class = ContratoSerializer

Conectar las direcciones en contratos/urls.py

Importante: router.register no crea ContratoViewSet. Solo conecta al router una clase que ya debe existir. En la plantilla de aprendices, el Mini 5 tiene TODOs en views.py y urls.py, así que es normal que esta ruta todavía no exista antes de completar esas piezas.
DefaultRouter genera las rutas a partir del ViewSet.

Registramos el nombre contratos. Mantenemos la ruta de diagnóstico existente y añadimos las rutas que genera el router.

from django.urls import path
from rest_framework.routers import DefaultRouter
from .views import EstadoJardinView, ContratoViewSet

router = DefaultRouter()
router.register('contratos', ContratoViewSet, basename='contrato')

urlpatterns = [
    path('estado/', EstadoJardinView.as_view(), name='estado-taller'),
    *router.urls,
]

Cómo se forma la URL completa

En config/urls.py ya existe el prefijo api/ que dirige las llamadas hacia contratos/urls.py. El router añade contratos/. Juntas, las dos piezas forman /api/contratos/. Esa es la colección de contratos.
GET /api/contratos/
Pide la colección. Esperamos HTTP 200.
GET /api/contratos/999999/
Pide un registro inexistente. Esperamos HTTP 404.

Recorrido que debes pedirles explicar

Cuando React solicita contratos, manda una petición HTTP a la URL. Django encuentra la ruta, el ViewSet consulta el modelo, el ORM lee PostgreSQL, el serializer prepara JSON y Django lo devuelve. React recibe ese JSON y lo muestra. Esa es la cadena que acabamos de construir.
