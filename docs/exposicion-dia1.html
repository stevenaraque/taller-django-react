Mini 1 - La Boveda - 6:00 a 6:25

Archivo: Backend/.env

Concepto que debes explicar

Django necesita saber a que base de datos conectarse. Esa informacion (usuario, clave, host, puerto) no se escribe en el codigo porque seria inseguro compartirla. Se guarda en un archivo .env que cada persona tiene en su equipo y que Git ignora. Django lo lee al arrancar gracias a python-dotenv.

La mision comprueba dos cosas: que PostgreSQL responde (base_datos: true) y que el motor es PostgreSQL y no SQLite (motor_bueno: true). El taller prohibe SQLite porque queremos que aprendan con el motor real que usaran en produccion.

Guion - di esto palabra por palabra

Vamos a abrir la boveda: el archivo que guarda las credenciales de la base de datos. Copien .env.example como .env y reemplacen los valores de ejemplo con los de su PostgreSQL.
La SECRET_KEY es la firma de Django. No la inventen: generemosla con el comando que esta en la guia. DEBUG=True significa modo de desarrollo: Django muestra errores detallados. En produccion se pone False.
Ahora ejecutamos tres comandos en orden: check busca errores de configuracion, migrate crea las tablas internas de Django, y runserver arranca el servidor en el puerto 8000.
Abran http://127.0.0.1:8000/api/estado/ en el navegador. Deben ver base_datos: true y motor_bueno: true. Si ven false, el problema esta en el .env, no en el codigo.

Pasos exactos

  1. Copiar Backend/.env.example a Backend/.env.
  2. Completar SECRET_KEY, DEBUG=True, DB_NAME=taller_django_react, DB_USER, DB_PASSWORD, DB_HOST=localhost, DB_PORT=5432.
  3. Activar el entorno virtual: .\venv\Scripts\Activate.ps1.
  4. Ejecutar: python manage.py check
  5. Ejecutar: python manage.py migrate
  6. Ejecutar: python manage.py runserver
  7. Abrir una segunda terminal y arrancar React: cd Frontend && npm install && npm run dev
  8. En el panel, pulsar Sondear la boveda.

Mini 2 - El Arquitecto - parte 1 - 6:25 a 6:55

Archivo: Backend/contratos/models.py

Concepto que debes explicar

Un modelo en Django es una clase de Python que describe una tabla de la base de datos. Cada atributo de la clase es una columna. Django traduce esa clase a SQL con las migraciones. El modelo Contrato guarda seis campos que vienen del dataset SECOP II: identificador, entidad compradora, descripcion, valor total, estado y fecha de firma.

__str__() define como se muestra un contrato en el Admin y en la consola. Meta.ordering hace que las consultas salgan ordenadas por identificador, lo que simplifica la paginacion y la busqueda.

La migracion es el archivo que Django genera para crear la tabla. makemigrations la genera, migrate la aplica en PostgreSQL. La tabla se llama contratos_contrato (app + modelo) y no debe renombrarse.

Guion - di esto palabra por palabra

Ahora disenamos la tabla donde viviran los contratos. Un modelo es una clase Python que describe las columnas. Cada campo de la clase es una columna de PostgreSQL.
Los seis campos vienen del dataset SECOP II: el identificador del contrato, la entidad que compra, la descripcion u objeto, el valor total, el estado y la fecha de firma. No guardamos todo el dataset: solo lo que el taller necesita.
CharField es texto corto, TextField texto largo, DecimalField dinero con decimales, DateField fecha. unique=True en el identificador evita duplicados.
__str__ hace que en el Admin se vea el identificador en vez de Contrato object (1). Meta.ordering ordena las consultas automaticamente.
Ahora generamos la migracion: makemigrations contratos. Django lee el modelo y escribe un archivo Python con las instrucciones SQL. Luego migrate ejecuta ese SQL en PostgreSQL.
Comprueben en /api/estado/: tabla_contratos debe pasar a true. Si sigue en false, la migracion no se aplico.

Pasos exactos

  1. Abrir Backend/contratos/models.py.
  2. Escribir la clase Contrato con los seis campos.
  3. Agregar __str__() que devuelva self.id_contrato.
  4. Agregar class Meta: ordering = ['id_contrato'].
  5. Ejecutar: python manage.py makemigrations contratos
  6. Ejecutar: python manage.py migrate
  7. En el panel, pulsar Sondear y verificar tabla_contratos: true.

Codigo completo - models.py

from django.db import models


class Contrato(models.Model):
    id_contrato = models.CharField(max_length=60, unique=True)
    entidad_compradora = models.CharField(max_length=180)
    descripcion = models.TextField(blank=True)
    valor_total = models.DecimalField(max_digits=16, decimal_places=2)
    estado = models.CharField(max_length=20, default='Activo')
    fecha_firma = models.DateField()

    class Meta:
        ordering = ['id_contrato']

    def __str__(self):
        return self.id_contrato

Mini 3 - El Jefe Maestro - 7:00 a 7:30

Archivo: Backend/contratos/admin.py

Concepto que debes explicar

Django trae un panel de administracion listo para usar en /admin/. Para que un modelo aparezca ahi, hay que registrarlo con admin.site.register() o con el decorador @admin.register(). Un ModelAdmin permite configurar que columnas se ven, como se busca y como se filtra, para que el Admin sea util con miles de contratos.

El juez del taller (EstadoJardinView) revisa si el modelo esta registrado en admin.site._registry. Si esta, modelo_en_admin es true. Ademas debe haber al menos un contrato creado manualmente para que contratos_registrados sea mayor o igual a 1.

Guion - di esto palabra por palabra

Django trae un panel de administracion gratuito en /admin/. Es la mesa de trabajo donde ustedes van a ver y crear contratos. Pero Django no sabe que modelos mostrar hasta que se los registren.
Vamos a registrar Contrato con un ModelAdmin propio. Configuramos list_display para ver las columnas importantes, search_fields para buscar por identificador, entidad o descripcion, y list_filter para filtrar por estado y fecha.
Ahora crean su usuario administrador con createsuperuser. Entren a http://127.0.0.1:8000/admin/ e inicien sesion. Veran la lista de contratos. Crean uno de prueba a mano.
Con los 5000 contratos reales de SECOP II cargados, el Admin deja de ser una vista vacia: se convierte en la herramienta para encontrar y revisar contratos por estado, entidad y valor.

Pasos exactos

  1. Abrir Backend/contratos/admin.py.
  2. Importar admin y Contrato.
  3. Crear ContratoAdmin(ModelAdmin) con list_display, search_fields y list_filter.
  4. Registrar con @admin.register(Contrato).
  5. Ejecutar: python manage.py createsuperuser (elegir usuario y clave).
  6. Abrir http://127.0.0.1:8000/admin/ e iniciar sesion.
  7. Crear un contrato de prueba desde la interfaz.
  8. En el panel, pulsar Sonar el panel.

8:00 a 9:00 - Mini 4 El Escudo

Objetivo de la hora: serializer que valida datos y rechaza negativos. Al terminar, los dos ataques del panel responden 400.

Mini 4 - El Escudo - 8:00 a 8:30

Archivo: Backend/contratos/serializers.py

Concepto que debes explicar

Un serializer convierte objetos de Python a JSON (para responder) y valida el JSON que llega (para crear o actualizar). ModelSerializer genera automaticamente los campos a partir del modelo. El escudo rechaza datos invalidos antes de que toquen la base de datos: si envias valor_total: "hola", Django responde 400 con el detalle del error.

Ademas, el escudo extra usa extra_kwargs para imponer min_value = 0 en valor_total: un contrato no puede tener valor negativo. El panel lanza dos ataques seguidos: un JSON malformado y un contrato completo pero con valor negativo; los dos deben rebotar con 400.

Guion - di esto palabra por palabra

Ahora construimos el escudo: el serializer. Su trabajo es traducir entre Python y JSON en las dos direcciones, y validar lo que entra.
ModelSerializer lee el modelo y genera los campos automaticamente. No hay que escribirlos a mano.
El escudo rechaza datos invalidos antes de que toquen la base. Si envias valor_total: "hola", Django responde 400 con el detalle del error. Eso es lo que el panel comprueba.
Escudo extra: con extra_kwargs imponemos que valor_total no acepte negativos. Un contrato no puede tener valor negativo. El panel lanza dos ataques: un JSON malformado y un contrato completo pero con valor negativo. Los dos deben rebotar.
Si la ruta responde 404, es porque aun no completaron el Mini 5 (el ViewSet y la ruta). Completen el Mini 5 primero y vuelvan.

Pasos exactos

  1. Abrir Backend/contratos/serializers.py.
  2. Importar serializers y Contrato.
  3. Crear ContratoSerializer(serializers.ModelSerializer) con Meta: model = Contrato, fields = '__all__', extra_kwargs = {'valor_total': {'min_value': 0}}.
  4. En el panel, pulsar Los dos ataques.

Codigo completo - serializers.py

from rest_framework import serializers
from .models import Contrato


class ContratoSerializer(serializers.ModelSerializer):
    class Meta:
        model = Contrato
        fields = '__all__'
        extra_kwargs = {'valor_total': {'min_value': 0}}

Verificacion

Los dos ataques responden HTTP 400. El panel muestra bloqueado en ambas filas de la tabla.

9:00 a 10:00 - Mini 5 El Velocista

Objetivo de la hora: API CRUD funcionando. Al terminar, GET /api/contratos/ responde 200 y GET /api/contratos/999999/ responde 404.

Mini 5 - El Velocista - 9:00 a 9:35

Archivos: Backend/contratos/views.py y Backend/contratos/urls.py

Concepto que debes explicar

Un ModelViewSet de DRF genera automaticamente las cinco operaciones CRUD (listar, crear, consultar, actualizar, borrar) para un modelo. Un DefaultRouter crea las rutas URL a partir del ViewSet. Juntos convierten ~50 lineas de codigo en ~5.

La mision comprueba dos cosas: GET /api/contratos/ responde 200 (la coleccion existe) y GET /api/contratos/999999/ responde 404 (el recurso fantasma no existe, lo que demuestra que la ruta de detalle funciona).

Guion - di esto palabra por palabra

Ahora la parte veloz: un ViewSet genera las cinco operaciones CRUD automaticamente. Listar, crear, consultar, actualizar y borrar, todo en una clase.
El router conecta esa clase a las URLs. En vez de escribir cada ruta a mano, el router las crea por nosotros.
La prueba lanza dos peticiones: GET /api/contratos/ debe dar 200 (la coleccion existe) y GET /api/contratos/999999/ debe dar 404 (el recurso no existe). El 404 demuestra que la ruta de detalle funciona.
Reinicien runserver despues de cambiar urls.py, porque Django carga las rutas al arrancar.

Pasos exactos

  1. Abrir Backend/contratos/views.py.
  2. Importar viewsets, Contrato y ContratoSerializer.
  3. Crear ContratoViewSet(viewsets.ModelViewSet) con queryset = Contrato.objects.all() y serializer_class = ContratoSerializer.
  4. Abrir Backend/contratos/urls.py.
  5. Crear router = DefaultRouter() y registrar: router.register('contratos', ContratoViewSet, basename='contrato').
  6. Agregar *router.urls a urlpatterns.
  7. Reiniciar runserver.
  8. En el panel, pulsar Correr la arena del Velocista.

Codigo completo - views.py (ViewSet)

from rest_framework import viewsets
from .models import Contrato
from .serializers import ContratoSerializer


class ContratoViewSet(viewsets.ModelViewSet):
    queryset = Contrato.objects.all()
    serializer_class = ContratoSerializer
